# 萊吉多人力與薪酬管理中心：第一階段現況差異盤點

## 1. 盤點結論

現有系統已具備員工主檔、月排假、兼職預設工時、單日班次、跨店支援摘要、30分鐘人力矩陣及月排班確認基礎，可以深化，不需推翻重做。但現行資料模型仍以「單一職稱、每人每日單一班次、整月整店解鎖、固定門店群組需求」為核心，與已核定第一階段規格存在結構性差距。

安全做法是保留現有資料表與讀取能力，先新增相容欄位及新表，再以adapter建立新讀取模型；待核對報告通過後，才指定完整月份切換新模組為唯一寫入來源。

|---|---|---|---:|
| 員工欄位分類 | `role_name`同時承載職稱與人員類別 | 新增僱用類型、工作類別及帳號關聯；保留`role_name`相容 | 高 |
| 人員狀態 | 只有`is_active` | 新增待到職、在職、留停、離職、停用及生效日 | 高 |
| 調店歷史 | 直接保存目前店碼 | 新增員工門店歸屬歷程，不覆蓋過去 | 高 |

| S01／S06管理 | 程式預設且只在S06暫停營業時允許代管 | 改為依有效管理關係判斷，S06營業後仍可由S01管理 | 高 |
| 月排假稽核 | 只保留最新內容與`updated_by` | 新增前後內容、原因與異動歷程 | 中 |
| 月排假權限 | 總部角色範圍偏廣 | 依COO、人資、授權總務、管理門店範圍重整RLS | 高 |
| 班次適用對象 | 編輯器限定兼職人員 | 支援正職、兼職及所有可排班人員 | 中 |
| 人力矩陣 | UI只明確呈現五甲矩陣 | 改為所有授權門店共用元件 | 中 |
| 班表視圖 | 部分資料來自既有展示型`scheduleRows` | 改由正式班次與需求模型投影 | 高 |
| 角色權限 | 模組權限與資料權限未完全對齊核定矩陣 | 新增排假、核准、成本及個資遮蔽能力判斷 | 高 |

## 4. 必須新增的正式能力

| 能力 | 新增內容 | 原因 |
|---|---|---|
| 多段班 | 移除每人每日唯一限制，改為班次ID及重疊防護 | 現況每人每天只能一筆，無法支援雙頭班 |
| 崗位與技能 | 崗位主檔、員工技能、班次崗位 | 現況只有職稱，不能判斷現場技能覆蓋 |
| 時段需求 | 每日基準、星期30分鐘需求及特殊日期覆蓋 | 現況每群組只有單一`demand`數字 |
| 支援申請 | 缺員店、支援店、人員、時段、核准人及狀態 | 現況可直接建立支援班次，沒有完整核准閉環 |
| 限範圍解鎖 | 指定日期、員工、班次、一次提交及24小時到期 | 現況核准後可修改整個申請門店與月份 |
| 班表版本 | 草稿、已發布、總部確認、待重新確認及版本明細 | 現況只有月份鎖定，沒有正式發布版本 |
| 異動歷程 | 班次前後內容、修改人、原因、核准人及版本 | 現況只保存最新班次與建立人 |
| 排班預估成本 | 預估薪資設定、班次成本分攤及門店成本率 | 現況沒有正式成本domain及安全資料欄位 |
| COO資料遮蔽 | 個人數字預設遮蔽、理由解鎖、逾時及查看稽核 | 現況只有一般安全模式，未形成薪資專用閉環 |
| 發布輸出 | 手機圖片、PDF、A4、LINE版本及版本差異 | 現況排假只匯出CSV |
| 個人班表連結 | 限本人、隨機識別、期限、撤銷及新版提示 | 現況沒有員工免登入安全查看方式 |
| 切換控制 | 指定月份、舊介面唯讀、新模組單一寫入 | 現況沒有新舊班表切換開關 |

## 5. 目前最重要的結構風險

### 5.1 每人每日只能一筆班次

`daily_staff_shifts`目前以`(shift_date, staff_id)`作唯一限制，repository也以同一條件覆蓋舊資料。若直接增加雙頭班畫面，第二段班會覆蓋第一段班，必須先處理資料模型。

### 5.2 解鎖範圍過大

現有修改申請只記月份與門店，核准後該門店可修改整個月份；尚未具備指定日期、員工、班次、一次提交與24小時失效。

### 5.3 門店代管依暫停營業判斷

目前資料庫函式要求受管門店為`suspended`才允許協調店代管。這與「南華恢復營業後仍由五甲管理」的核定規則衝突，須改成生效中的管理關係，不以營業狀態決定代管權。

### 5.4 人資資料語意混合

現有`role_name`同時被用於職稱、兼職判斷及有效人力排除。若直接增加總部人員或新的工作類別，排班與權限判斷容易錯誤，必須先拆分僱用類型、職稱與工作類別。

### 5.5 班表展示與正式班次尚未統一

月排假頁已有正式單日班次資料，但週／月班表視圖仍主要依`scheduleRows`呈現。若未先建立統一投影模型，總部可能看到的班表與實際儲存班次不同。

## 6. 安全開發批次

### 批次A：領域與相容資料模型

1. 建立僱用類型、職稱、工作類別、狀態及員工帳號關聯模型。
2. 建立員工歸屬店歷程與門店管理關係有效期間。
3. 建立崗位、技能及班次崗位模型。
4. 建立需求規則domain：基準、星期30分鐘及特殊日期。
5. 全部新增欄位允許空值，既有`role_name`與店碼繼續可讀。

**驗收關卡：**既有人員與門店關係正規化前後筆數一致，S01、S05、S06、S09對應不變。

### 批次B：多段班與正式班次投影

1. 讓同一員工同日可有多筆班次。
2. 建立同人、同日、跨店的時間重疊阻擋。
3. 正職與兼職共用班次命令，不再限定兼職編輯器。
4. 將排假、預設工時、單日班次及跨店支援投影成統一班表模型。
5. 將所有門店接入共用30分鐘矩陣。

**驗收關卡：**原單日班次完整保留；雙頭班、重疊班、支援班及排除角色測試通過。

### 批次C：需求、人力成本與管理看板

1. 建立門店需求設定與特殊日期覆蓋。
2. 建立排班預估時薪、月薪換算及跨店成本分攤。
3. 建立個人成本遮蔽與查看稽核。
4. 總部看全店比較，門店只看本店人力與成本摘要。

**驗收關卡：**需求優先順序、成本歸屬、門店隱私及COO遮蔽測試通過。

### 批次D：發布、鎖定與支援閉環

1. 建立班表版本及發布狀態。
2. 建立正式跨店支援申請與核准。
3. 將修改申請限制為日期、員工或班次，加入一次提交與24小時到期。
4. 重新提交後自動鎖定並等待總部再確認。

**驗收關卡：**門店無法越權修改其他店、非核准範圍、過期申請或已使用申請。

### 批次E：輸出與切換

1. 產生手機圖片、PDF、A4及LINE分享版。
2. 建立可撤銷、有限期限的個人班表連結。
3. 建立舊資料唯讀核對報告與指定月份切換控制。
4. 先以S01五甲及S06南華情境試行，再擴至其他門店。

**驗收關卡：**新舊筆數與工時一致、正式月份只有一個寫入來源、舊資料可查且未被改寫。

## 7. Supabase正式環境原則

- 本文件只依repository與migration檔案盤點，不代表所有migration已套用至目前正式Supabase。
- 開發前須先在開發分支查核實際資料表、constraint、RLS、RPC及資料筆數。
- 新migration先在開發Supabase套用並執行回歸測試，不直接在正式專案貼SQL。
- migration不得刪除現有欄位、班次、排假、員工或門店關係。
- 正式切換前需輸出舊資料基準、轉換後核對及可回復方案。

## 8. 下一個執行單位

先執行批次A中的「員工分類與相容模型」，因為班次、需求、成本、權限及後續薪資都依賴這個基礎。完成domain、adapter、測試與開發migration後，先在本機及開發Supabase驗收，不部署正式資料變更。
